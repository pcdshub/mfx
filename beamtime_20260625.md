### 2.4 Verify the stream

In a second terminal on the same machine (the PVs are served locally):

```bash
pvget -r value ami:ana:graph:data:goal
pvget -r value ami:ana:graph:data:centroids
pvget -r value ami:ana:graph:heartbeat
```

`goal` should be the pixel you clicked, `centroids` should be `[cx, cy, rms]`, and
`heartbeat` should climb each time you re-run it. If no `ami:*` PVs show up at all,
the export is the problem; go back to 2.2.

## 3. Connect the AMI class from Python

In a shell, start hutch-python:

```bash
cd mfx
source mfxenv                          # Loading local disk python env pcds-5.9.1
hutch-python --cfg conf.yml
```

In hutch-python, import the alignment code and read the PVs through the AMI class:

```python
from mfx.optimize.vonhamos_align import (
    AMI, find_signal, align_yaw, optimize_focus,
    align_one_crystal, align_all_crystals,
)

ami = AMI()                 # connects over PVA, latches goal_x
ami.goal_x                  # the pixel you clicked
ami.centroid()              # (cx, cy), or None when the spot is off screen
ami.rms()                   # float, or inf when the spot is off screen
```

## 4. Single-crystal dry run

Only if the von Hamos is mounted and a crystal can produce signal. This is the first
time the real motors and the real centroid feedback run together.

In hutch-python, run the steps individually so you can stop at any point:

```python
spec.c1.rot.position                   # note where it starts
spec.c1.x.position

find_signal(spec.c1.rot, ami)          # sweeps rot until the spot appears
align_yaw(spec.c1.rot, ami)            # centers cx on goal_x
optimize_focus(spec.c1.x, ami)         # scans x, moves to minimum rms
```

| Check | Pass |
|-------|------|
| `find_signal` | `True`, prints the rot where signal appeared |
| `align_yaw` | `converged True`, `err` within tol |
| `optimize_focus` | `converged True`, clear rms minimum |

Then the full chain with the manual checkpoint:

```python
align_one_crystal(spec.c1, ami)        # interactive=True by default
```

## 5. Parameters to pin down

| Parameter | Function | Default | What it means |
|-----------|----------|---------|---------------|
| `step` | `find_signal` | 2.0 deg | `find_signal` sweeps rot in increments of this size looking for the spot. If the step is larger than the rot range over which the spot is visible, the sweep can jump right over it, so it has to be smaller than that window. |
| `nudge` | `align_yaw` | 0.5 deg | before centering, `align_yaw` moves rot by this much once and measures how far the spot shifts, to learn the pixels-per-degree sensitivity. It should be big enough for a clear shift and small enough that the signal stays on the detector. |
| `tol` | `align_yaw` | 1.0 px | the centering target. `align_yaw` stops once the spot's cx is within this many pixels of goal_x. |
| `max_step` | `align_yaw` | 2.0 deg | a safety cap. No single yaw correction moves rot more than this, so a bad sensitivity estimate cannot fling the motor. |
| `span` | `optimize_focus` | 2.0 mm | `optimize_focus` scans x from this far below to this far above the current position. It must be wide enough that the rms minimum falls inside the scan. |
| `steps` | `optimize_focus` | 11 | how many x points the focus scan samples across that span. More points resolve the minimum better but take longer. |
| `fresh_events` | `AMI` | 3 | each PV read waits for this many new events before trusting the centroid, so the reading averages over enough shots to be stable. |

The two that decide whether the loop works at all are `step` in `find_signal` (must
be finer than the signal window) and `span`/`steps` in `optimize_focus` (must
bracket a real minimum without running into the no-signal region).
